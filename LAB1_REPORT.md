## What this lab was actually about

Going in, I didn't really get why we needed a whole separate tool (DVC) on top of git — isn't git supposed to version everything? Turns out the reason clicked once I actually ran into it myself: **git and DVC solve two different problems that happen to live in the same folder.** Git is great at tracking small text files and knowing exactly what changed between two versions of code. It is not built for a gigabyte of JPEGs — it would try to diff binary files, bloat the repo history forever, and GitHub outright rejects pushes past a certain size anyway. DVC's trick is that it never actually asks git to store the real bytes. Instead, DVC hashes your data, stores the actual content somewhere else (for this lab, DagsHub), and hands git a tiny text file — a "pointer" — that basically says *"here's the hash of what the data folder is supposed to contain."* Git versions the pointer, DVC versions the data behind it, and as long as the two move together, your code and your data stay in sync commit-by-commit.

Once I saw it working end-to-end (especially the fresh-clone test in Question 7), it stopped feeling abstract. Everything below is me actually going through it.

## Setting up the project

I started from a completely empty GitHub repo named `mlops-lab-1`, cloned it locally, and ran:

```bash
uv init
```

I'd never used `uv` before either (I'd only ever used plain `pip` + `venv` in previous classes), so this part was as much "learn the tool" as "do the lab."

### Question 1 — what did `uv init` create?

It scaffolded a minimal Python project: `pyproject.toml` (the project manifest — name, Python version requirement, and eventually the dependency list), `.python-version` (pins the interpreter version so `uv run` always uses the same Python, currently 3.12), a placeholder `main.py`, and an empty `README.md`. Nothing exciting on its own, but it's apparently the standard modern-Python project skeleton — no `requirements.txt`, no virtualenv I have to remember to activate myself, `uv` just handles that later once dependencies show up.

### Setting up DVC

```bash
dvc init
git add .dvc .dvcignore
git commit -m "Initialize git and dvc"
git push
```

I actually got stuck right here before even getting to the interesting part: `dvc` wasn't recognized as a command at all, which was confusing since `pip show dvc` clearly said it was installed. Took a bit of digging to understand what was going on — I had two different Python installations on my laptop, and `pip install dvc` had put it into a user-scripts folder that belonged to the *other* one, not the one my terminal actually used. First instinct was to just edit my PATH manually, but the cleaner fix (and apparently the more "correct" way to install standalone CLI tools like this) was `uv tool install dvc`, since `uv` already had its own bin folder on PATH. That fixed it right away.

### Question 2 — what does `dvc init` create, and what should go to git?

It creates a `.dvcignore` file at the root (same idea as `.gitignore`, but for DVC — tells it what to skip when scanning folders) and a `.dvc/` directory containing:
- `.dvc/config` — the **shared** project config (remote names, URLs, defaults). This is meant to be committed — everyone on the team needs to see it.
- `.dvc/.gitignore` — auto-generated by DVC itself, and this is the important one: it tells git to *never* track `.dvc/config.local`, `.dvc/tmp/`, or `.dvc/cache/`. Those are exactly the places where secrets and the actual local data cache live.

So the short answer: `.dvc/config` and `.dvcignore` get pushed to git. `.dvc/cache` and any `config.local` never do — and DVC is set up so you'd almost have to go out of your way to accidentally commit them.

### Connecting DagsHub as the DVC remote

```bash
dvc remote add --global origin https://dagshub.com/georges2.2004/mlops-lab-1.dvc
dvc remote modify origin --global auth basic
dvc remote modify origin --global user georges2.2004
dvc remote modify origin --global password <token>
dvc remote default origin

git add .dvc/config
git commit -m "Configure DagsHub as dvc remote"
git push
```

I signed up on DagsHub (also a first for me) and created a matching `mlops-lab-1` repo there, then generated an access token from the DagsHub settings instead of typing in my actual account password — the site itself nudges you toward this, and it made sense once I thought about it: a token can be revoked on its own without touching my actual login.

I definitely fumbled the command order at first — I ran `dvc remote modify origin --global auth basic` before the remote even existed yet, and got a `remote 'origin' doesn't exist` error. Then separately I ran the `user` command but forgot to actually type my username after it, which gave a weirder error about an "expected str for dictionary value." Neither was a big deal to fix once I slowed down and read the error properly instead of just re-running the same thing, but it was a good reminder that these CLI tools really do expect the commands in a specific order and won't guess what you meant.

### Question 3 — where do the credentials actually live?

`--global` writes to a config file that lives in *my user profile*, completely outside of any git repository (on Windows, under `AppData\Local\iterative\dvc\config`). It's not project-specific — it applies to every DVC project I have on this machine. The alternatives:
- no flag at all → writes to the shared `.dvc/config` (**never put a password here**, it's git-tracked)
- `--local` → writes to `.dvc/config.local`, which is scoped to just this project but stays on this machine only (and is already excluded by DVC's own `.gitignore`, as I noted above)
- `--system` → machine-wide, for every user account on the computer, needs admin rights

Should credentials go to GitHub? Obviously not, and the nice part is that with any of these options they physically can't — none of them write into a file git would ever see.

### Adding the raw data

The lab wants:
```
./data/food11_raw/training
./data/food11_raw/evaluation
./data/food11_raw/validation
```

I downloaded the Food-11 zip from Kaggle and extracted it straight into that structure — 9,866 training images, 3,430 validation, 3,347 evaluation, all named like `<category-index>_<n>.jpg` where the number before the underscore maps to one of the 11 categories (0 = Bread, 1 = Dairy product, ... 10 = Vegetable-Fruit).

```bash
dvc add data
```

### Question 4 — what happened to `.gitignore`?

It got a single new line added: `/data`. That's DVC telling git *"stop looking at this folder entirely, I've got it."* From this point on, git has zero visibility into what's inside `data/` — DVC owns tracking it completely.

### Question 5 — what's in `data.dvc`?

It's tiny, just a handful of lines:
```yaml
outs:
- md5: a3a457d03c51ff8b037a833440f6ad13.dir
  size: 1188442712
  nfiles: 16643
  hash: md5
  path: data
```
The `.dir` hash is computed over a manifest of every file inside `data/` plus their individual hashes — not a hash of a single file. `size` and `nfiles` matched exactly what I had on disk (1.2GB across 16,643 files). This ~6-line file is what actually gets pushed to GitHub instead of the 1.2GB of images.

```bash
git add data.dvc .gitignore
git commit -m "Track data folder with dvc"
git push
dvc push
```

**A practical detour here:** pushing the full 1.2GB to DagsHub over my connection was going to take a long time, and my instructor had mentioned we didn't need to push the entire dataset for this lab to be complete. So I split things up: I kept the complete 16,643-image dataset in a second folder, `data_local/`, which I added to `.gitignore` so git/DVC never touch it — it's purely my own local working copy for actually running the processing script on real data. Meanwhile `data/` (the one DVC tracks and pushes) started out with just a handful of sample images per split, so the whole git+DVC workflow stayed fast to demonstrate and push while I was actively working through the lab. At the very end, once everything else was working, I went back and pushed the *entire* dataset properly through `data/` anyway (see the final section below) — so the finished repo does end up with the complete dataset tracked, this was just how I paced getting there.

### Question 6 — checking GitHub and DagsHub

On GitHub, browsing the repo shows the code (`main.py`, `pyproject.toml`, etc.), the DVC config files, and `data.dvc` — but no `data/` folder at all. No actual images ever touch GitHub.

On DagsHub, the repo's data browser actually lets you see and click through the tracked files as if they were normal files in the repo — that's DagsHub's whole value proposition over just using GitHub, since GitHub has no idea DVC-tracked data even exists.

### Question 7 — cloning fresh

I cloned the repo into a completely separate temp folder to check. Right after cloning: no `data/` folder anywhere, just `data.dvc`. Running:

```bash
dvc pull
```

fetched the tracked files from DagsHub and materialized the full `data/` folder, exactly matching what `data.dvc` described. This is the moment where the git/DVC split really makes sense end-to-end: `git clone` gets you code + a promise about what the data should look like, `dvc pull` is what actually cashes in that promise.

## Processing the images

The lab wants a script that takes the raw images and produces two new datasets shaped the way an image classifier (something like ResNet via `ImageFolder`) expects — one folder per category, images resized down to 128×128:

```
data/food11_processed/<split>/<category>/*.jpg
data/food11_processed_mini/<split>/<category>/*.jpg   (capped at 100 images per category per split)
```

I wrote this as `src/food11/data.py`. The logic is fairly simple once you break it down:
1. For each split, list the raw images.
2. Pull the category index off the front of the filename (everything before the first `_`) and map it to one of the 11 category names.
3. Open the image, convert to RGB (just in case any weren't already), resize to 128×128, and save it under the matching category folder in `food11_processed`.
4. Keep a running count per split/category, and as long as it's under 100, also save a copy into `food11_processed_mini`.

Added Pillow as a dependency for the actual image handling:
```bash
uv add pillow
```

and ran it with:
```bash
uv run python ./src/food11/data.py
```

I tested it first against my small tracked `data/` sample (worked instantly, produced the right folder structure), then ran it for real against the full `data_local/` copy. End result on the full dataset: all 16,643 raw images processed successfully, sorted correctly into all 11 category folders, and the mini datasets landed close to the expected ~100-per-category cap (exactly 1,100 for training since every category had at least 100 images there; slightly under for evaluation/validation since a couple of categories had fewer than 100 images available in those smaller splits).

```bash
dvc add data
git add data.dvc pyproject.toml uv.lock src/
git commit -m "Add food11_processed and food11_processed_mini"
git push
dvc push
```

## Question 8 — checking out an old commit

```bash
git log --oneline -- data.dvc
git checkout <old-commit-hash>   # the very first data.dvc, before processing existed
dvc checkout
```

At that older commit, `data/` only contained `food11_raw` — **`food11_processed` and `food11_processed_mini` did not exist.** That makes complete sense once you think about it: `dvc checkout` restores the working directory to *exactly* whatever `data.dvc` said at that point in history, and at that commit I hadn't written the processing script yet. It's the same principle as checking out an old commit in a normal git-only repo and not seeing a file that gets added later — DVC just extends that same guarantee to the data folder.

```bash
git checkout main
dvc checkout
```

brought everything back to the current state.

Once the rest of the workflow was proven out, I went back and replaced the small sample in `data/` with the complete contents of `data_local/` (all 16,643 raw images plus their processed and mini versions), re-ran `dvc add data`, and pushed the full dataset to DagsHub for real. So the final state of the repo has the complete Food-11 pipeline properly tracked end-to-end — nothing left as a stand-in sample.

## Takeaways

Going into this lab I honestly thought DVC was going to feel like a redundant extra step on top of git, and coming out of it I don't think that anymore. The biggest thing that clicked is how cleanly git and DVC's jobs are separated — git never even tries to understand your data, DVC never tries to replace git for code, they just agree on a tiny pointer file as the handoff between them. It's a simple idea but it took actually breaking things (the PATH issue, the out-of-order remote commands, watching `data/` disappear after a fresh clone) for it to really sink in rather than just being something I read in a slide.

The credential scoping (`--global` vs. plain vs. `--local`) also made way more sense once I saw the three side by side instead of just reading about them abstractly — once you know exactly which physical file each one writes to, the "is this safe to commit" question kind of answers itself. I still want to get more comfortable with the DVC/git interaction in general (especially the `dvc checkout` timing relative to `git checkout`), but for a first lab I feel like I actually understand *why* the workflow is shaped the way it is, not just the commands to type.
